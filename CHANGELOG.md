### Unreleased
- **Fix: Android regression — nothing reached Adobe (neither email nor push token).** `e2f55ba` made `ACPCampaign_Cordova.setPushIdentifier` return an error *before* `MobileCore.collectPii` when the device token was empty/missing. Apps that call before Firebase produces a token used to still deliver the email (the empty token only made `setPushIdentifier("")` a no-op), so the guard silently blocked everything — "yesterday the email arrived, today nothing does". The token is now optional: an empty/missing token only skips the push registration (logged via `Log.w("ACP_CAMPAIGN", …)`) while the PII is still collected, and the call succeeds when at least the token or the PII was delivered. Also hardened against JSON `null`/non-object arguments (`optString`/`optJSONObject` instead of throwing `JSONException`) and the email is additionally sent under the configured `TYPE_ID` key so attributes populated before the `emailaddress` key rename keep refreshing.
- **Fix: Android token forwarding never fired.** The automatic Firebase forwarding in `www/ACPCampaign.js` only subscribed to `onTokenRefresh`, which fires when the token *changes* — an existing FCM token was therefore never forwarded (contradicting the README). The module now also calls `firebasePlugin.getToken(...)` immediately on `deviceready` (handles both callback- and Promise-style plugins) and only then subscribes to refreshes. The `contextData` normalization also uses a local `isObject` helper instead of the bare `acpIsObject` global, removing a load-order `ReferenceError` risk that could abort the exec call entirely. Diagnostics: Android now logs `ACP_CAMPAIGN: setPushIdentifier: sent token=…, pii keys=…` so the bridge output can be verified with `adb logcat -s ACP_CAMPAIGN`.
- **Feature: full Adobe Campaign Standard push tracking (impression "7" / click "2" / open "1") for Android and iOS.** Per Adobe's "Implementing Push tracking" guide:
  - **Android dismiss/click tracking now actually fires.** `NotificationDismissedReceiver` was declared with package `com.galp.bluetooh` while `plugin.xml` registered the relative `.NotificationDismissedReceiver` (which resolves against the *app* package), and `FirebasePluginMessagingService` never set a `setDeleteIntent` — so swipe-away (action "2") was never reported. The receiver now uses the plugin package `com.adobe.marketing.mobile.cordova`, `plugin.xml` registers the fully-qualified name, and the Firebase plugin (cordova-plugin-firebase-only-analytics-notifications-OS) wires `setDeleteIntent` to it by class-name string (no compile dependency; no-op when cordova-acp is absent). The receiver also collects custom payload keys as PII for parity with the receipt/tap paths and iOS.
  - **Android click/open de-duplication.** A cold start from a notification tap called `handleMessage` from both `pluginInitialize()` and `onResume()`, sending actions "2"/"1" twice; `onNewIntent` had the same re-send risk. `wasHandled` is now set right after handling.
  - **iOS foreground impression fixed.** The Firebase plugin's `willPresentNotification` posted `FirebaseRemoteNotificationClickedDispatch`, so a mere foreground arrival was tracked as click+open ("2"+"1"); it now posts the *Received* dispatch → impression ("7") per Adobe's guidance. Taps still send "2"+"1".
  - **iOS dismiss/click tracking implemented.** `ACPAppDelegatePush` registers the `DEFAULT` notification category with `.customDismissAction` (payload must set `aps.category = "DEFAULT"`), and the Firebase plugin branches on `UNNotificationDismissActionIdentifier` to post a new `FirebaseRemoteNotificationDismissedDispatch`, which `ACPAppDelegatePush` turns into a click-only `collectMessageInfo` (action "2", no open, no deep link).
  - **iOS UNUserNotificationCenter delegate hijack removed.** `ACPCampaign_Cordova.setPushIdentifier/loadAdobe` set `center.delegate = self` while implementing no delegate methods, stealing the delegate from the Firebase plugin and silently disabling every tracking dispatch (and foreground presentation). The assignment and the now-unused `UNUserNotificationCenterDelegate` conformance were removed — the Firebase plugin keeps the delegate, as intended since the first commit.
  - Requires paired changes in `fafvaz/cordova-plugin-firebase-only-analytics-notifications-OS` (deleteIntent + iOS dispatch fixes); both plugins must be updated together.
- **Fix: Android MABS build failure (`ACPFirebaseMessagingService.java`).** `MobileCore.collectPii()` accepts `Map<String, String>`, but the PII map built from custom FCM payload keys was declared `HashMap<String, Object>`, failing `:app:compileDebugJavaWithJavac` with `incompatible types: HashMap<String,Object> cannot be converted to Map<String,String>`. The map is now `HashMap<String, String>` (all FCM payload values are Strings).
- **Fix: iOS MABS build failure (`ACPCampaign_Cordova.swift`).** The archive failed with exit code 65 and 4 Swift errors at lines 78/136: `extraneous argument label 'identifier:' in call` and `cannot convert value of type 'String' to expected argument type 'Data'`, which MABS reported as *"The Cordova plugin cordova-acp/cordova-adobe-acp is not compatible with the 'Swift Language Version' build setting"*. AEPCore's real signature is `MobileCore.setPushIdentifier(_ deviceToken: Data)` — no argument label and a `Data` parameter — while the plugin called the non-existent `setPushIdentifier(identifier:)` with the token `String` coming from JS. The token is now decoded to `Data` first (`pushTokenData(from:)`: APNs hex format incl. `<>`/space wrappers; non-hex tokens such as opaque FCM tokens pass through as UTF-8, mirroring Android's `MobileCore.setPushIdentifier(String)`), and an empty token is logged and skipped instead of sent.
- Restored `self.typeId = Bundle.main.object(forInfoDictionaryKey: "TypeId")` initialization in `ACPCampaign_Cordova.loadAdobe` (present in 58fbab7, lost in a later refactor) so the fiscal number is added to contextData even when `loadAdobe` runs before `setPushIdentifier`.
- **Fix: `ACPCore.getAppId()` returned null on Android.** The runtime lookup `webView.getPreferences().getString("APP_ID")` could never see the plugin variable: Cordova persists plugin variables (Extensibility Configurations) in config.xml as `<variable>` elements inside `<plugin>`, and cordova-android's `ConfigXmlParser` only parses `<preference>` elements (verified against the framework source), ignoring `<variable>`. The legacy `AppId` string resource is also dropped on MABS 12+. Fixed by: (a) `plugin.xml` now injects `<preference name="APP_ID" value="$APP_ID"/>` / `<preference name="TYPE_ID" value="$TYPE_ID"/>` into the app's `res/xml/config.xml`; (b) native code additionally parses the packaged `res/xml/config.xml` for the `<variable>` values as a fallback; (c) `getAppId` now returns a descriptive `APP_ID_NOT_CONFIGURED` error to the bridge instead of a silent null, and lazily configures the SDK if the id is only found at call time. Same fallback applied to `ACPCampaign_Cordova` TYPE_ID.
- MABS 12+ compatibility: cordova-android 13 renamed `res/values/strings.xml` to `res/values/cdv_strings.xml` and MABS ignores plugin config-file injections targeting `res/values/*strings*.xml`, so the `AppId`/`TypeId` string resources were never present in the APK (crash: `Resources$NotFoundException: String resource ID #0x0` on startup in `ACPCore_Cordova.initialize`).
- `ACPCore_Cordova` and `ACPCampaign_Cordova` now read `APP_ID` / `TYPE_ID` from the config.xml preferences (plugin variables), keeping the string resources only as a legacy fallback. A missing value no longer crashes the app; it is logged and the Adobe SDK is simply not configured.
- Still compatible with MABS 11 (cordova-android 12), where the string-resource injection continues to work.
- **Fix: iOS push tracking not working.** `ACPAppDelegatePush.registerExtensions()` registered `NotificationCenter` observers using `self` — which in a `static func` is the metatype (`ACPAppDelegatePush.Type`), not an `NSObject` instance. `NSNotificationCenter` invokes selectors via `performSelector:`, so observers bound to a metatype never fire and push tracking (impression/click/dismiss) was silently dropped. A `shared` instance is now used as the observer target, and the three handler methods (`handleNotificationDispatched`, `handleClickNotificationDispatched`, `handleDismissDispatched`) are instance methods so `performSelector:` can dispatch them correctly.
- **Fix: iOS push token not reaching Firebase.** `AppDelegate+Push.m` swizzled `application:didRegisterForRemoteNotificationsWithDeviceToken:` but never forwarded to the original implementation, so `[FIRMessaging messaging].APNSToken = deviceToken` in the Firebase plugin never ran and push notifications could not be delivered. The swizzled method now calls the original implementation after registering the token with Adobe.
