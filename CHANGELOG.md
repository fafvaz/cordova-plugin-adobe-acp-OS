### Unreleased
- **Fix: `ACPCore.getAppId()` returned null on Android.** The runtime lookup `webView.getPreferences().getString("APP_ID")` could never see the plugin variable: Cordova persists plugin variables (Extensibility Configurations) in config.xml as `<variable>` elements inside `<plugin>`, and cordova-android's `ConfigXmlParser` only parses `<preference>` elements (verified against the framework source), ignoring `<variable>`. The legacy `AppId` string resource is also dropped on MABS 12+. Fixed by: (a) `plugin.xml` now injects `<preference name="APP_ID" value="$APP_ID"/>` / `<preference name="TYPE_ID" value="$TYPE_ID"/>` into the app's `res/xml/config.xml`; (b) native code additionally parses the packaged `res/xml/config.xml` for the `<variable>` values as a fallback; (c) `getAppId` now returns a descriptive `APP_ID_NOT_CONFIGURED` error to the bridge instead of a silent null, and lazily configures the SDK if the id is only found at call time. Same fallback applied to `ACPCampaign_Cordova` TYPE_ID.
- MABS 12+ compatibility: cordova-android 13 renamed `res/values/strings.xml` to `res/values/cdv_strings.xml` and MABS ignores plugin config-file injections targeting `res/values/*strings*.xml`, so the `AppId`/`TypeId` string resources were never present in the APK (crash: `Resources$NotFoundException: String resource ID #0x0` on startup in `ACPCore_Cordova.initialize`).
- `ACPCore_Cordova` and `ACPCampaign_Cordova` now read `APP_ID` / `TYPE_ID` from the config.xml preferences (plugin variables), keeping the string resources only as a legacy fallback. A missing value no longer crashes the app; it is logged and the Adobe SDK is simply not configured.
- Still compatible with MABS 11 (cordova-android 12), where the string-resource injection continues to work.
